# Nagame Pre-trip Companion Plan

สถานะ: `GO_LIVE_CANDIDATE`
วันที่: 2026-08-25
ขอบเขต: product direction และ go-live candidate; production release gates ยังคงแยกต่างหาก

## 1. ตำแหน่งของผลิตภัณฑ์

> **Nagame คือเพื่อนคนไทยที่ช่วยเตรียมตัวไปญี่ปุ่น ตั้งแต่ยังไม่รู้จะไปไหน จนพร้อมออกเดินทาง**

Tomarigi ช่วยตอบว่า “ตอนนี้สถานที่นั้นเป็นอย่างไร” ผ่านแผนที่และกล้องสด
Nagame ต้องตอบว่า “คุณควรไปที่ไหน เตรียมอะไร และทำอย่างไรให้ทริปนี้เหมาะกับคุณ”

## 2. งานหลักที่ต้องชนะ

ผู้ใช้ควรเดินทางผ่านลำดับนี้:

`บอกความต้องการ → กร๊วกช่วยตัดสินใจ → ได้แผนเตรียมตัว → บันทึกเป็นทริป → ใช้ต่อระหว่างเดินทาง`

จุดแตกต่างที่ต้องรักษาไว้:

- **เข้าใจคน**: จำช่วงเวลา งบ จังหวะการเที่ยว ข้อจำกัดอาหาร และความชอบ
- **ช่วยตัดสินใจ**: อธิบายเหตุผลและ trade-off ไม่ใช่แค่แสดงรายการสถานที่
- **ทำให้ลงมือได้**: คำตอบจบด้วย next action หรือ checklist ที่ทำต่อได้
- **ต่อเนื่อง**: สิ่งที่คุยก่อนเดินทางต้องกลับมาใช้ใน Trip และ During-trip mode

## 3. ประสบการณ์หลักของ Pre-trip Companion

หน้าแรกยังเป็นแชทกร๊วก พร้อมทางเข้า 3 แบบ:

1. **ยังไม่รู้จะไปไหน** — แนะนำเมือง/ช่วงเวลาให้เหมาะกับผู้ใช้
2. **รู้เมืองแล้ว ช่วยเตรียมทริป** — สร้าง brief, checklist และสิ่งที่ควรจอง
3. **มีทริปแล้ว ช่วยเช็กความพร้อม** — ตรวจช่องว่างของแผนและสิ่งที่ยังไม่ได้เตรียม

คำตอบหลักของกร๊วกควรมี 4 ชั้น:

1. คำแนะนำแบบเพื่อน: สรุปสั้นและบอกเหตุผล
2. หลักฐานประกอบ: ฤดู อากาศ งบ การเดินทาง กล้องสด หรือคำเตือนเมื่อเกี่ยวข้อง
3. สิ่งที่ทำต่อได้: ปุ่ม/การ์ด เช่น “เลือกเมืองนี้”, “เพิ่มเข้าทริป”, “เช็กที่พัก”
4. ความต่อเนื่อง: บันทึกสิ่งที่ตัดสินใจแล้วไว้ใน Trip เป็น card ที่ผู้ใช้จัดการเอง

กล้องสดและแผนที่เป็น **evidence layer** ที่กร๊วกหยิบมาใช้ ไม่ใช่หน้า catalog หลัก

## 4. ลำดับการทำงาน

### Phase 1 — Decide: เลือกทิศทางทริป

- รับข้อมูลขั้นต่ำ: เดือน/จำนวนวัน/งบ/สไตล์/ข้อจำกัดสำคัญ
- แนะนำเมืองหรือช่วงเวลา 1–3 ทางเลือก พร้อมเหตุผลและข้อแลกเปลี่ยน
- แสดง weather/season และข้อมูลสดเท่าที่มีจริง
- ให้ผู้ใช้ยืนยันทางเลือกหนึ่งแล้วสร้าง trip brief

### Phase 2 — Prepare: เปลี่ยน brief เป็นความพร้อม

- สร้าง checklist แยกเป็น `ควรตัดสินใจ`, `ควรจอง`, `ควรเตรียม`, `ควรรู้`
- เพิ่มเที่ยวบิน ที่พัก ร้านอาหาร และการเดินทางเข้า Trip ผ่านการสนทนา
- แสดงสถานะความพร้อมและ next action เดียวที่สำคัญที่สุด
- รองรับปัจจัยไทยที่มีผลจริง เช่น THB, ฮาลาล/มังสวิรัติ/แพ้กุ้ง, Suica, internet, เงินสด, เสื้อผ้า

### Phase 3 — Go: ใช้ต่อระหว่างเดินทาง

- เปลี่ยนคำทักทายและลำดับความสำคัญเป็น “วันนี้”
- เช็กอากาศ/คำเตือน/การเดินทางของวันนั้น
- ช่วยสลับแผนเมื่อฝนตก เหนื่อย หรือสถานที่ไม่เหมาะ
- ส่งต่อเส้นทางให้ Google Maps/แอป transit แทนการสร้างระบบนำทางเอง

## 5. สิ่งที่ยังไม่ทำในรอบแรก

- full-screen globe แบบ Tomarigi
- camera directory ระดับประเทศหรือระดับโลก
- การเพิ่ม provider กล้องใหม่เพียงเพื่อให้เหมือน reference
- หน้า grid รวมเมืองที่ทำให้ Nagame กลับไปเป็น catalog
- dashboard ข้อมูลจำนวนมากที่ไม่มีคำแนะนำจากกร๊วกเป็นกรอบ
- กฎบังคับหนึ่งวันหนึ่งหมุดหรือ itinerary ที่ตายตัว

## 6. Local-first card package

- IndexedDB เป็น working store ของ pre-trip plan แทนการเขียน `localStorage` โดยตรง
- อ่านข้อมูลจาก key เดิมได้ครั้งเดียวเพื่อย้ายข้อมูลโดยไม่ทิ้งของผู้ใช้
- Export/import ไฟล์ `.nagame` เป็นทางสำรองและทางย้ายเครื่อง
- Card status: `เก็บไว้`, `สำคัญ`, `เสร็จแล้ว`; ผู้ใช้กรอง แก้สถานะ หรือนำออกเองได้
- ยังไม่อ้างว่าเป็น persistent memory ข้ามเครื่อง; cloud sync/auth ต้องเป็น gate แยก

## 7. ขั้นถัดไปที่แนะนำ

ทำ implementation package เดียวก่อน:

> **Pre-trip Companion: “รู้เมืองแล้ว ช่วยเตรียมทริป”**

เหตุผล: ใช้โครงสร้างแชทและข้อมูลเมืองที่มีอยู่แล้ว, วัดคุณค่าได้เร็ว, และทำให้ความต่างจาก Tomarigi เห็นชัดที่สุด

Definition of Done รอบนี้:

- ผู้ใช้ระบุเมือง/ช่วงเวลา/งบ/สไตล์ผ่านแชทได้
- กร๊วกตอบพร้อมเหตุผลและหลักฐานข้อมูลที่มีจริง
- ผู้ใช้กดยืนยันแล้วได้ trip brief และ checklist ที่อ่านรู้เรื่อง
- รายการที่เลือกเพิ่มเข้า Trip ได้
- มี empty/error/fallback state ที่ไม่หลอกว่าข้อมูลสดพร้อมเสมอ
- มี rendered UI evidence บน desktop และ mobile

ข้อจำกัดหลัก: prototype/local persistence ใช้พิสูจน์ workflow ได้ แต่ยังไม่ใช่หลักฐานของ LINE Login, persistent memory, provider E2E หรือ production readiness; สิ่งเหล่านั้นต้องเป็น approval gate แยก

## 8. ขั้นตอนปฏิบัติหลังแผนนี้

1. สร้าง Task Contract สำหรับ Pre-trip Companion

3. ตรวจ flow ปัจจุบันของ chat → cards → Trip แล้วออกแบบจุดต่อที่เล็กที่สุด

5. รัน focused checks และทดสอบ rendered state desktop/mobile
