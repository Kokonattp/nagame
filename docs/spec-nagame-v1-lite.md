## 1. ปัญหา → สิ่งที่อยากได้

**ตอนนี้:** แชทกับกร๊วกตอบเป็นการ์ดหลายหมวด วางเส้นทางหรือแผนรายวันไม่ได้, production ตอบ rule-based เพราะ key LLM ใช้ไม่ได้

**อยากได้:** ผู้ใช้คุยกับ **ทาบิ** (แมว) แล้วได้ร่างทริปญี่ปุ่นที่ใช้ได้จริง:
1. เข้าใจคำขอภาษาไทยแบบคลุมเครือ
2. ถามกลับเฉพาะสิ่งที่ขาด ครั้งละ 1 ข้อ
3. เสนอ ≤3 ทาง พร้อมเหตุผลสั้น
4. ปรับตามที่คุย ("คนน้อยกว่านี้", "ขอมีออนเซ็น", "อันแรก") โดยไม่รื้อทริป
5. ได้ร่างทริปรายวัน เก็บไว้เปิดกลับมาได้

> กฎสูงสุด: **ผู้ใช้ต้องรู้สึกว่าง่าย แม้เบื้องหลังจะซับซ้อน**

## 2. หลักการที่ห้ามหลุด

1. **Jev เลือก ไม่แต่ง.** ทุกสถานที่/เส้นทาง/ประโยคที่ขึ้นจอ มาจากชุดตัวเลือกที่ code เตรียม (ข้อมูลจริงหรือแม่แบบ) — Jev แค่เลือก จัดอันดับ และตัดสิน
2. **ข้อมูลสดต้องมี source + เวลาเช็ก.** ไม่มี = ทาบิบอก "ควรเช็กก่อนไป" ห้ามแสดงตัวเลข
3. **≤3 ตัวเลือกต่อครั้ง** — บังคับใน code
4. **ไม่มีโหมดให้เลือก, ไม่โชว์ความคิดภายใน**
5. **งบต่อข้อความ:** Jev ≤3 request, เวลารวมเป้า < 2 วินาที (ไม่นับค้นตั๋ว)
6. **ไม่ผูกกับผู้ให้บริการเดียว.** การตัดสินใจทั้งหมดผ่าน interface `Decider` — Jev เป็นตัวหลัก, Laya (open-weights, รันในเครื่อง) เป็นตัวสำรอง
7. **ความมั่นใจต่ำ = ถามกลับ.** ถ้า `confidence` ของคำตอบหลักต่ำกว่าเกณฑ์ (ตั้งจากผล M0) ทาบิถามยืนยันแทนการเดา

## 3. ส่วนประกอบ

```text
ผู้ใช้ ⇄ ทาบิ (UI)
          │
          ▼
   /api/tabi  ── Decider (interface)
          │        ├─ JevDecider    (TypeSafe, ตัวหลัก)
          │        └─ LayaDecider   (สำรอง, ยังไม่ทำใน V1)
          │
          ├─ Place store   : สถานที่ ~2,000 จุด + คะแนนที่คำนวณไว้ล่วงหน้า
          ├─ Route builder : code จับกลุ่ม/เรียง/ประมาณเวลา
          ├─ Phrase bank   : ประโยคแม่แบบทาบิ
          └─ Flight scout  : worker JEV UltraFast (optional, local)
```

| ส่วน | ทำอะไร | ใครทำ |
|---|---|---|
| เข้าใจคำขอ | intent, อ้างถึงอะไร, ต้องค้นสดไหม, ความชอบ | Jev (`choice` + `noul`) |
| ดึงตัวเลข | จำนวนวัน, เดือน, วันที่ | code (regex ภาษาไทย) |
| หา candidate | กรองสถานที่ตามภูมิภาค/ประเภท/ฤดู/คะแนน | code |
| จัดอันดับให้ตรงคน | rerank 20–30 candidate ตามคำขอคนนั้น | Jev (`score` ต่อ candidate, ถามรวดเดียว) |
| ประกอบเส้นทาง | จับกลุ่มตามพิกัด, เรียงลำดับ, แบ่งวัน, เวลา "ประมาณ" | code |
| พูดไทย | เลือกประโยคแม่แบบ + เติมชื่อ/เหตุผลจาก tag | Jev (`choice`) + code |
| ข้อมูลสด | ราคาตั๋ว | Flight scout |

## 4. ข้อมูล

### 4.1 แหล่ง
| แหล่ง | ใช้อะไร | สัญญาอนุญาต |
|---|---|---|
| Wikidata | ชื่อ (EN/JA), พิกัด, ประเภท (`instance of`), จังหวัด, จำนวน sitelinks | CC0 |
| Wikipedia (EN) summary | ข้อความสั้นให้ Jev อ่านตอนให้คะแนน | CC BY-SA — ไม่แสดงข้อความนี้บนจอ ใช้เป็น input เท่านั้น |
| Wikivoyage | ข้อความฤดู/ช่วงปิดของเส้นทาง | CC BY-SA — ถ้าแสดง ต้องมี credit |
| Wikipedia images | ภาพการ์ด (service เดิม `lib/services/city-images.ts`) | ตามเงื่อนไขภาพ + credit |
| Muse (แอปของเจ้าของ) | เจ้าของใช้ช่วยค้นข้อมูลเส้นทาง/ช่วงปิด → เจ้าของตรวจก่อนนำเข้า | ไม่ใช่ส่วนของแอป, ไม่มี API |

### 4.2 คลังสถานที่
- เป้า ~2,000 จุด: สถานที่ท่องเที่ยวในญี่ปุ่นที่มีบทความ Wikipedia ≥ 5 ภาษา (ปรับเกณฑ์ตามผล M0)
- **คำนวณไว้ล่วงหน้า (ชั้น 1, ทำครั้งเดียว):**
  | มิติ | วิธี |
  |---|---|
  | ประเภท (onsen / shrine-temple / nature / city / food / museum / theme park) | code จาก Wikidata ก่อน, Jev `choice` เมื่อ code ไม่แน่ใจ |
  | ภูมิภาค | code จากจังหวัด |
  | คนเยอะแค่ไหน (1–5) | Jev `score` |
  | ฤดูที่ดีที่สุด | Jev `choice` (spring / summer / autumn / winter / all-year) |
  | เหมาะไปครั้งแรก / พาเด็ก | Jev `noul` |
- **คิดตอนคุย (ชั้น 2):** Jev rerank candidate ตามคำขอของผู้ใช้คนนั้น
- งบโดยประมาณ: 2,000 จุด × 1 request × ~1,500 token ≈ 3 ล้าน token (ยืนยันด้วย M0)

## 5. Agent loop (ตาม spec เต็ม §6.2)

```text
ข้อความ + tripState
  → code: ดึงตัวเลข (วัน, เดือน)
  → Jev request #1 (รวดเดียว): intent, อ้างถึงอะไร, ต้องค้นสดไหม, ความชอบที่พูดถึง
  → DECIDE (code):
       ข้อมูลไม่พอ / confidence ต่ำ → ถาม 1 ข้อ + chip
       เสนอ/ปรับ → candidate จาก Place store → Jev request #2 rerank → Route builder
       ถามตั๋ว → Flight scout (async) + การ์ด deep-link ทันที
  → Jev request #3 (ถ้าต้อง): เลือกประโยคแม่แบบ
  → ตอบ: ฟองข้อความ + payload ≤3
```

### intent (Jev `choice`)
`start_trip` · `refine` · `pick_option` · `ask_detail` · `add_stop` · `draft_itinerary` · `ask_flight` · `smalltalk` · `other`

### ความชอบ (Jev `noul` หลายข้อในครั้งเดียว)
nature · snow · onsen · food · shopping · culture · fewer_crowds · easy_travel · family · scenic_photo

## 6. หน้าตาและ animation

ตาม mockup 5 หน้าจอ + tokens (spec เต็ม §27): `#F7FBFF` `#2D7FF9` `#0C1F4A` `#FFE9F2` `#FF5C9D` `#E8F8F0` `#FF9E45`, การ์ดมุม 18–28px, IBM Plex Sans Thai

**ต่างจาก mockup โดยตั้งใจ:** ผู้ช่วย = แมวทาบิ, ไม่มีราคาที่ไม่มี source, ไม่ใช้โลโก้สายการบิน, เวลาเดินทางเขียน "ประมาณ", ภาพจาก Wikipedia + fallback พื้นสี

**Animation (จากวิดีโอ):** ทาบิวิ่งบน day stepper · timeline ไล่ขึ้น · การ์ดเด้งเมื่อเลือก · ทาบิพิมพ์ "…" · การ์ดใหม่ fade-in หลังปรับ · checkbox pop
กติกา: transform/opacity, ≤400ms, ปิดได้ด้วย `prefers-reduced-motion`, ห้ามลอกไอคอน/ภาพจากวิดีโอ

**ภาพทาบิ:** ใช้ภาพกร๊วกเดิมผ่าน registry ไปก่อน → เปลี่ยนจุดเดียวเมื่อเจ้าของทำภาพใหม่

## 7. ตั๋วบิน

- ค่าเริ่มต้น: การ์ด deep-link Google Flights ตามช่วงวัน (ผ่าน `buildOutbound()`)
- ถ้า worker เปิดอยู่: JEV UltraFast ค้น โดย **แทน `field_text()` ด้วย Jev `choice`** เลือกค่าจากรายการที่ code รู้ (ต้นทาง, ปลายทาง, วันไป, วันกลับ) → ไม่ต้องใช้ LLM ภายนอก
- cache ผลตาม "เส้นทาง + วันที่" หลายชั่วโมง, ค้นเฉพาะเมื่อผู้ใช้ขอ
- เว็บกัน bot / CAPTCHA → หยุดทันที, แสดงการ์ด deep-link, ห้ามพยายามข้าม
- ข้อจำกัดเดิม: search-only, ไม่ login/จอง/จ่าย/กรอกข้อมูลส่วนตัว
- worker ต้องรันเป็น process ค้าง (มี Chrome) → **รันบน Vercel ไม่ได้**; V1 = local เท่านั้น

                    preferences: string[]; avoid: string[] };
type Trip = {
  id: string; title: string; status: "exploring" | "draft" | "planned";
  createdAt: string; updatedAt: string;

## 9. M0 — ทดสอบความเป็นไปได้ (ก่อนทำหน้าจอ)

โฟลเดอร์: `experiments/m0/` (ไม่แตะแอป)

| Test | ทำอะไร | เกณฑ์ผ่าน |
|---|---|---|
| M0-A Triage | 20 ประโยคไทย → intent + ความชอบ + ต้องค้นสดไหม; **รันทั้ง Jev และ Laya ด้วยชุดเดียวกัน** | intent ถูก ≥ 85% (17/20) |
| M0-B Place scoring | 64 สถานที่จาก Wikidata (เป้าเดิม 100 — Wikidata throttle query ที่ใหญ่กว่า) → คะแนน 4 มิติ → เจ้าของตรวจ | เจ้าของเห็นด้วย ≥ 80% ต่อมิติ (มิติที่ไม่ผ่าน = ตัดหรือเปลี่ยนวิธีถาม) |
| M0-C Cost & speed | วัดจาก A + B | ≤ 2,000 token และ ≤ 500 ms ต่อ request (ค่ากลาง) |
| M0-D Flight | ค้น BKK → TYO 1 ครั้ง โดย Jev เลือกค่ากรอก | ได้ผลบนหน้าจอ หรือโดนบล็อกพร้อมบันทึกอาการ (ทั้งสองแบบ = ได้ข้อมูลตัดสินใจ) |

**ผลลัพธ์ M0:** ตาราง PASS/FAIL ต่อ test + จำนวน token จริง → เจ้าของตัดสินว่าไป M1 หรือปรับโครง

**Jev vs Laya:** Laya มี server ในเครื่องที่ใช้ wire protocol เดียวกับ Jev (`POST /v1/systemone`) → `Decider` สลับได้ด้วยการเปลี่ยน URL.
เลือกตัวหลักจากผล M0-A (ความแม่นภาษาไทย) — ไม่ใช่จากราคาอย่างเดียว. Laya รันบน Vercel ไม่ได้ (ต้องมีเครื่องที่ค้าง process + โหลด model ~0.3–0.4B)

### ผล M0 (2026-10-10) และสิ่งที่ M1 ต้องปรับ

| Test | ผล |
|---|---|
| M0-A | PASS — intent 20/20, median 309 ms, ~1,000 token |
| M0-B | PASS — crowd 88%, season 97%, first-timer 93%, family 97% (ผู้ตรวจ: Claude ตามที่เจ้าของมอบหมาย, ตัดออก 5 จุดที่ปิด/เข้าไม่ได้) |
| M0-C | PASS |
| M0-D | Jev กรอกฟอร์มครบโดยไม่ใช้ LLM, หน้าผลลัพธ์ Google ขึ้น "Oops, something went wrong" (โปรไฟล์ Chrome ใหม่เอี่ยม) |

**ข้อบังคับเพิ่มใน M1:**
1. คลังสถานที่ต้องกรองที่ปิดแล้ว: Wikidata `P576` (dissolved/closed) + Jev `noul` "ปิดถาวร/เข้าไม่ได้"
2. คำถามคนเยอะถามแบบเทียบกับสถานที่ดัง (Jev ให้สูงเกินจริงกับวัดที่ไม่ดัง)
3. เกณฑ์ `noul` ของ "ต้องค้นสด" และความชอบ = 0.7; ความชอบดูจากข้อความผู้ใช้เท่านั้น ไม่ส่งบริบทเส้นทาง
4. ช่วงปิดตามฤดู (เช่น Tateyama ปิดหน้าหนาว) ห้ามเชื่อคะแนน Jev อย่างเดียว — ใช้ข้อมูลที่ตรวจแล้วใน `data/places/seasonal-closures.json`
5. การ์ดตั๋วใน M1 = ลิงก์ผลค้นหา Google Flights ตามวันของทริป; ตั๋วสด (worker) = M2

## 13. ความเสี่ยง

| ความเสี่ยง | ทางกัน |
|---|---|
| Jev เข้าใจภาษาไทยไม่แม่น | M0-A วัดก่อน; confidence ต่ำ = ถามกลับ |
| คะแนนเชิงความรู้สึก (คนเยอะ) ผิด | M0-B ให้เจ้าของตรวจ; มิติที่ไม่ผ่านตัดทิ้ง |
| ทาบิพูดแข็งเพราะใช้แม่แบบ | ประโยคหลายแบบต่อสถานการณ์; LLM ขัดภาษาเป็นชั้นเสริมเมื่อมีงบ |
| เวลาเดินทางคลาดเคลื่อน | แสดง "ประมาณ"; ไม่คำนวณตารางรถไฟ |
| ช่วงปิดของสถานที่ไม่มีในข้อมูลเปิด | Jev อ่าน Wikivoyage + ข้อมูลที่เจ้าของตรวจจาก Muse; ทาบิเตือนให้เช็กเว็บทางการ |
| เว็บตั๋วกัน bot | ตั๋วเป็นของเสริม, cache, deep-link fallback, ไม่ข้าม CAPTCHA |
| TypeSafe ขึ้นราคา/เปลี่ยนเงื่อนไข | interface `Decider` + Laya สำรอง |
| Next.js เวอร์ชันนี้ต่างจากที่คุ้น | อ่าน `node_modules/next/dist/docs/` ก่อนเขียน route (AGENTS.md) |
